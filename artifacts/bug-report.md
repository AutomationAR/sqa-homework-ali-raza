## BUG-1 — Suggested prompts are served by the API and never rendered

**Severity:** High (silent feature loss + dead content-management surface)
**Environment:** https://ask.permission.ai, unauthenticated, Chromium 151, desktop 1440x900 and Pixel 5

### Steps to reproduce
1. Open https://ask.permission.ai in a **fresh** browser profile (no prior session).
2. Observe the chat: agent header, one greeting bubble, composer. **No suggestion
   pills anywhere on the page.**
3. Confirm the backend does serve them:
   ```bash
   curl -s https://ask.permission.ai/api/agent/suggestions-unauthenticated | jq '.[] | {title, enabled, for_authenticated}'
   # no jq? this needs nothing but the browser:
   #   fetch('/api/agent/suggestions-unauthenticated').then(r => r.json()).then(console.table)
   ```
4. Confirm they are absent from the page rather than hidden — DevTools console:
   ```js
   ['What is Permission','Best way to earn ASK','Permission Wallet']
     .filter(t => document.documentElement.outerHTML.includes(t))
   // → []  (not merely display:none — the markup was never rendered)
   ```
5. Automated: `npm run recon` → `verify-suggestions` re-verifies this contract and
   regenerates the screenshot + evidence note below.

### Actual
The endpoint returns **200** with **six** records, every one `enabled: true` and
`for_authenticated: false`:

| order | title | prompt |
|---|---|---|
| 1 | What is Permission | What is Permission? |
| 2 | Best way to earn ASK | How can i earn ASK? |
| 3 | How permission uses my data | How permission uses my data? |
| 4 | What is passive earning | What is passive earning? |
| 5 | What is data ownership | What is data ownership and why it is important for me? |
| 6 | Permission Wallet | What is Permission Wallet? |

The page requests this endpoint on load (confirmed in the network log,
`artifacts/recon/21-network-streams.json`) and renders none of it.

### Expected
Enabled, unauthenticated suggestions appear as selectable prompts.

### Evidence that it is dropped, not merely hidden
`artifacts/recon/50-suggestion-render-samples.json` samples the page every 2s for
20s and checks all six titles against three surfaces:

| surface | result |
|---|---|
| `document.body.innerText` | no match, all 10 samples |
| `document.documentElement.outerHTML` | no match — so not hidden by CSS either |
| any inline `<script>` payload | no match |

A wide net over `button, a, li, [role=button], [class*=chip\|pill\|badge\|suggest\|topic\|prompt\|card]`
returned only the header buttons and footer links
(`artifacts/recon/13-pill-hunt.json`).

### Evidence regenerated on demand

```bash
npm run recon        # or: npx playwright test --config=recon/recon.config.ts verify-suggestions
```

`recon/verify-suggestions.spec.ts` re-verifies the defect live and rewrites its
proof into `artifacts/bug-evidence/`, so nothing in this write-up rests on a
screenshot someone took by hand months ago:

| File | Contents |
|---|---|
| `bug-1-1440x900.png` | Full-page screenshot — `Log in`/`Sign Up` header, one greeting bubble, and the empty region where the six pills belong |
| `bug-1-evidence.md` | Self-contained note: the six titles expected, `0/6` in visible text **and** `0/6` in raw HTML, `Log in` present with `0` authenticated widgets (state proof), every control the page *did* render, and the verbatim API payload |

Generator: `recon/evidence.ts`.

### Negative controls — two competing explanations, both ruled out

Re-checked 2026-08-15. Both alternatives to "the app drops the data" were tested
directly, because either one would have made this report wrong:

| Explanation | Test | Result |
|---|---|---|
| The suite carries a **stale session** and is seeing the post-login UI | `recon/verify-suggestions.spec.ts` logs the context's `storageState` *before* navigation and the page's own state after → `artifacts/recon/70-clean-context-check.json` | **Ruled out.** 0 cookies, 0 origins, `Log in` visible on the page. Anonymous by both measures, and still 0/6 titles across all 10 samples. |
| **Headless automation** is served different markup (UA sniffing / bot detection) | `recon/verify-suggestions-realchrome.spec.ts` — real Chrome (`channel:'chrome'`), headed, fresh profile, stock desktop UA, at 1440×900 and 393×851 → `artifacts/recon/71-real-chrome-check.json` | **Ruled out.** 0/6 titles and no “Suggested topics” label at either width. |

Two further points close the loop:

- The suite sets **no `storageState`** and has no auth project or global setup, so
  there is no mechanism by which a session could reach these tests. Independently,
  this app's session is **not restorable from a saved `storageState`** at all
  (`artifacts/recon/README.md`, `recon/capture-authenticated.js`) — reapplying a
  captured post-login state yields a logged-**out** page.
- The pills are absent from the human-in-the-loop **authenticated** capture too
  (`artifacts/recon/authenticated/desktop-00-landing-text.txt` — no titles, and no
  "Download Extension" CTA either). So this is **not** a post-login regression:
  the suggestions render in *no* state, which is consistent with the data being
  fetched and discarded.

### Impact
- A first-time visitor gets a blank chat with no examples of what the agent does.
  This is the app's entire onboarding affordance.
- The six rows carry `order`, `enabled` and `for_authenticated` flags and
  `updated_at` timestamps — someone maintains them. Editing them changes nothing
  in production, so the content surface is silently dead.
- `GET /api/agent/suggestions` (authenticated variant) returns **401** when
  anonymous, so the same feature likely exists for signed-in users and is worth
  checking there too.

### How this defect is asserted in the suite
The two required behaviours for this feature — "the pills are visible" and "clicking
a topic produces a response" — are **test 2**,
`tests/02-suggested-topics.spec.ts`, annotated **`test.fail()`**: a clean run reports
it as *expected failure*, so the suite stays green (`8 passed`, exit 0) while the
defect stays visible.

They share one test because the click is unreachable without the pill. Split, both
would fail on the identical assertion and spend two of eight slots reporting one
defect twice. Merged, the test walks the whole journey — API serves topics → pills
render → click posts *that topic's* prompt → a graded reply arrives — and stops at
the first thing that is broken, which today is step two.

The annotation is a tracker, not a shrug. `test.fail()` fails when the test
**passes**, so the moment the app renders the pills it reports "expected failure did
not occur", the annotation comes off, and it becomes an ordinary green test. Neither
the defect nor the fix can be reached silently.

Three alternatives were rejected:

- Asserting the pills **are** rendered, unannotated: red on every run against a
  defect the suite cannot fix. A permanently-red suite gets ignored.
- Asserting they are **absent**: codifies the bug as expected behaviour and then
  passes forever after someone fixes it.
- Leaving the test out: the requirement is unrepresented, and the next person has
  to rediscover why.

The reason the first attempt at `test.fail()` was withdrawn was a real hole, and
it is now closed rather than avoided. That attempt used
`getByText(title, { exact: false })`, which matched the agent's **own greeting**
whenever the model happened to say "what is Permission" — under `test.fail()`
that reports the defect as fixed (attempt 0 passed, the retry failed, Playwright
called it flaky). The current locator cannot do that:

1. the match is **anchored to a control's whole label**, not a substring;
2. only **interactive** elements count (`button`, `[role=button]`, `a`, `li`), so
   prose can never satisfy it;
3. the resolved element's **ancestors are checked** in the page before it is
   clicked, rejecting anything inside a chat bubble or the OneTrust widget
   (`tests/pages/ask-page.ts` → `suggestionPill`, `assertPillIsRealControl`).

That claim is itself tested, on the live page, by
`recon/verify-pill-locator.spec.ts`:

| Control | Setup | Result |
|---|---|---|
| **Positive** | Inject the pill markup the app *should* render — six buttons built from the live API payload, wired to the real composer — then run test 2's assertions unchanged | **Pass**: 6/6 pills detected, click issues `POST /ask-unauthenticated` carrying the topic's exact configured prompt, 200, one new agent bubble. So test 2 goes green the moment BUG-1 is fixed. |
| **Negative** | Inject a chat bubble whose text is exactly a topic title, including a link inside it | **0 pills reported.** The false positive that broke the first attempt is closed. |

```bash
npm run verify:pills                                    # both controls above
$env:EXPECT_PILLS=1; npx playwright test 02-suggested   # PowerShell: run test 2 strictly (red today)
EXPECT_PILLS=1 npx playwright test 02-suggested         # bash equivalent
```

**Test 3** picks up the part of this feature that is still reachable: it types the
top served topic's own `prompt` into the composer as free text and grades the reply
with the same rubric as the promptfoo eval. It passes today, and it catches something
nothing else does — a CMS topic whose prompt the agent can no longer answer, which is
currently invisible to everyone precisely *because* the pills are unreachable.

`recon/verify-suggestions.spec.ts` still regenerates the standalone evidence above
on demand.

## BUG-2 — Failed login dead-ends with no feedback

**Severity:** Medium (High for any user whose captcha does not resolve)

### Steps to reproduce
1. Go to https://ask.permission.ai/login.
2. Open DevTools → **Network**, filter to `Fetch/XHR`.
3. Enter a **correctly formatted** email and any password.
4. Click **Log in** and wait 20 seconds without touching anything.
5. Watch the submit button and the network panel.

Confirm the gate is a captcha — DevTools console:
```js
typeof window.grecaptcha                          // → "object"
!!document.querySelector('.grecaptcha-badge')     // → true
```

Automated (a captcha failing under automation is expected and correct):
```bash
npx playwright test --config=recon/recon.config.ts explore-authenticated
```

### Actual
The login form is gated by **invisible reCAPTCHA v2**
(`size=invisible`, `execute-ms=30000`, badge bottom-right —
`artifacts/recon/81-recaptcha.json`).

When the token does not resolve, clicking **Log in**:
- disables the submit button **permanently** — still disabled after 20s
- issues **no** authentication request to any host
- logs **no** console error
- shows the user **no** message, spinner, timeout or retry

Timeline and traffic capture: `artifacts/recon/82-login-outcome.json`.

Reproduced under automation, where a captcha failing is expected and correct.
The defect is not the captcha — it is that the failure path is invisible. A human
on a flaky network, a strict privacy extension, or a low-reputation IP hits the
same dead end with nothing to act on. There is no timeout and no error state.

**Expected:** a bounded wait, then an actionable error ("Could not verify your
browser — retry") with the button re-enabled.

## BUG-3 — Chat transcript is invisible to assistive technology

**Severity:** Medium (accessibility)

### Steps to reproduce
1. Open https://ask.permission.ai and send any question.
2. DevTools console:
   ```js
   Array.from(document.querySelectorAll('[aria-live],[role="log"],[role="status"],[role="alert"]'))
     .map(e => ({ tag: e.tagName, cls: e.className, isOneTrust: e.className.includes('ot-') }))
   ```
3. Count how many of the results are **not** OneTrust's.

**Result (verified 2026-08-15):** two matches, both `ot-scrn-rdr` (the third-party
cookie banner), both zero-size and invisible. **Non-OneTrust live regions: 0.**

4. Optional, with a screen reader (NVDA/VoiceOver): send a question and listen.
   Nothing is announced when the reply arrives.

### Actual
The transcript has no `aria-live` region, no `role="log"` and no `role="status"`.
The only live regions on the page belong to the third-party OneTrust banner
(`artifacts/recon/14-hooks-before.json`).

Because replies are injected without an announcement, a screen-reader user gets
no notification that the agent has answered — and since the composer is also
cleared and disabled during the request with no textual status, there is no
non-visual signal that anything is happening at all.

**Expected:** wrap the transcript in `role="log"` with `aria-live="polite"`, and
give the in-flight state a textual status announcement.

**Confirmed post-login too.** Across all eleven authenticated pages captured
(desktop and mobile), every page reports exactly two live regions — and both are
OneTrust's, both zero-size and invisible
(`artifacts/recon/authenticated/*-inventory.json`). The application contributes no
live region anywhere, signed in or not.

## BUG-4 — The agent has no conversation memory, and claims otherwise

**Severity:** High (core product behaviour)

### Steps to reproduce
1. Open https://ask.permission.ai.
2. Send: `Remember this codeword: ZEBRA42. Just confirm you got it.`
3. Send: `What was the codeword I just gave you?`

Automated reproduction (prints both replies and every request body):

```bash
npx playwright test --config=recon/recon.config.ts session
```

### Actual (verbatim, captured)
> **Turn 1 —** "I've noted the codeword ZEBRA42. I can also help explain how
> Permission.ai works…"
>
> **Turn 2 —** "**I cannot tell you the exact words you just used.** I'm here to
> help you with information about Permission.ai…"

The agent asserts it has stored the codeword, then cannot retrieve it one turn
later. Two failures in one: no memory, and a false claim of memory.

### Root cause is visible from the client
Every request body, across a whole conversation:

```json
[0] {"message":"hi","utmData":null,"sessionId":""}
[1] {"message":"Remember this codeword: ZEBRA42. Just confirm you got it.","utmData":null,"sessionId":""}
[2] {"message":"What was the codeword I just gave you?","utmData":null,"sessionId":""}
```

- `sessionId` is **`""` on every single request**, including the second and third.
- The response to each request **does** carry a session id to persist:
  `{"message":"…","session_id":"3b6be3a0-b043-4b66-87cb-a4de77ee0fb8"}`.
- The body carries **no history array** either.

So the client throws away the `session_id` the server hands it, and sends no
conversational context by any other means. Each turn is an independent
single-shot completion.

### Why this matters more than it looks
The UI is built as a conversation — a scrolling transcript, and replies that
actively invite follow-ups ("Would you like more details on one of these ways to
earn, or…?"). Accepting that invitation is exactly the interaction that fails: a
follow-up like "yes, tell me about the first one" has no antecedent. The product
sets an expectation on every turn that it cannot meet on the next.

### Data-layer consequence
The server mints a session row per message. Conversations cannot be reconstructed
by `session_id`, so per-conversation analytics (turns per session, drop-off point,
which topic leads to signup) are unavailable. See `artifacts/data-checks.md`.

## BUG-5 — Unresolved template variable used as a storage key

**Severity:** Low

### Steps to reproduce
1. Open https://ask.permission.ai in a fresh profile and wait for the greeting.
2. DevTools console:
   ```js
   Object.keys(localStorage)
   // → ["undefined-auto-message-sent", "lastExternalReferrerTime", …]
   ```
   Or DevTools → Application → Local Storage → `https://ask.permission.ai`.

**Result (verified 2026-08-15):** the first key is literally
`undefined-auto-message-sent`.

### Actual
`localStorage` on the anonymous landing page contains the key:

```
undefined-auto-message-sent
```

The literal string `undefined` is the interpolated value of a variable that was
never set — almost certainly `${userId}-auto-message-sent` evaluated before, or
without, a user. Every anonymous visitor therefore shares one global key. If it
gates the greeting bootstrap, its behaviour will differ between anonymous and
signed-in users in ways nobody intended.

Captured in the storage dump alongside BUG-4.

## BUG-6 — Every redeemable offer has expired; the earn loop is closed

**Severity:** High (the product's core value proposition is unreachable)
**Evidence:** `artifacts/recon/authenticated/desktop-redeem-text.txt`,
`desktop-data-enrichment-hub-text.txt`, `desktop-wallet-text.txt`

### Steps to reproduce
Requires a signed-in account. Login is captcha-gated, so sign in by hand — or run
`npm run capture:auth`, which opens a real browser, waits for you to log in, then
records each page read-only.

1. Log in at https://ask.permission.ai/login.
2. Open **Redeem**. Scan the section headings and every offer's date label.
3. Open **Data Enrichment Hub** → count the entries under "Top Offers For You".
4. Open **Wallet** → read the "Earn withdrawal minimum" panel and the progress meter.
5. Compare step 3's reward value against step 4's threshold.

Observed on a real account (100 ASK balance) on 2026-08-15:

**The Redeem page contains nothing redeemable.** Its only section is **"Past
Offers"**, and all eight entries are expired:

| Offer | Value | Label |
|---|---|---|
| Starbucks | 20,000 ASK | Ended on Sunday, June 1 |
| Apple | 20,000 ASK | Ended on Tuesday, July 1 |
| Nintendo | 40,000 ASK | Ended on Thursday, October 2 |
| Apple and iTunes US | 20,000 ASK | Ended on Friday, January 2 |
| Netflix | 40,000 ASK | Ended on Tuesday, April 1 |
| Spotify | 40,000 ASK | Ended on Monday, September 1 |
| Google Play — $10 | 40,000 ASK | Ended on Wednesday, January 7 |
| Google Play — $5 | 20,000 ASK | Ended on Sunday, June 1 |

There is no "Active" or "Current" offers section at all.

**The arithmetic makes the loop unwinnable.** The Data Enrichment Hub lists exactly
one live earning action under "Top Offers For You": *Permission User Survey,
25 ASK, 5 Minute Survey*. The Wallet enforces a withdrawal threshold of
**5,000 ASK** (meter reads `100 / 5,000`, "You have collected 2% of the ASK
needed"). One available action worth 25 ASK against a 5,000 ASK gate is **200
repetitions of the same survey** — and the survey is presumably once-only.

So a signed-up user is told by the agent that they can "earn ASK by sharing data,
completing surveys, and completing automations" and can view offers, then finds one
survey and a wall of expired coupons. Referrals pay 1,000 ASK each, making
referral the only realistic path to the threshold — which is not what the product
communicates.

**Expected:** at least one active offer, or explicit empty-state copy explaining
when new offers arrive. An expired-only list with no active section reads as a
broken page, not as "check back later".

**Note:** the **Withdraw ASK** button is correctly `[disabled]` at this balance —
that part works.

## BUG-7 — Withdrawal threshold copy contradicts itself

**Severity:** Low (copy/clarity)
**Evidence:** `artifacts/recon/authenticated/desktop-wallet-aria.txt` lines 43-47

### Steps to reproduce
1. Log in with an account holding **less than 5,000 ASK** (100 ASK in this case).
2. Open **Wallet**.
3. Read the "Earn withdrawal minimum" panel top to bottom — the sentence, then the
   meter, then the caption beneath it.
4. Compare the number in the sentence against the meter's upper bound.

### Actual
The same panel states, in this order:

> **"Due to transfer restrictions, you'll need at least 4,900 ASK to make a
> withdrawal."**
> `100 ————— 5,000` *(progress meter)*
> "4,900 ASK needed to withdraw"

The threshold is **5,000 ASK**; 4,900 is the *shortfall* from the current 100
balance. The first sentence states the shortfall as though it were the threshold, so
a user reading only that line concludes they need 4,900 total — and would be wrong
by their own balance. The two later elements are correct.

**Expected:** "You need 5,000 ASK to withdraw — 4,900 to go."

### Also worth tightening (same page)
Three balance figures appear with no stated relationship: "Total Balance 100 ASK",
"Pending 100 ASK", and "Wallets 0 ASK / Permission wallet 0 ASK". The entire
balance is pending and none of it is in a wallet, which is coherent once explained
but is presented as three unexplained numbers.

## Open question — not reported as a defect

The mobile landing capture (`mobile-00-landing-text.txt`) renders **"Log in /
Sign Up"** while the same capture session shows "Welcome Ali!" on a later route,
which looked like a flash of unauthenticated state on first paint.

I could not confirm it. Re-running with the saved `storageState`
(`recon/auth-hydration.spec.ts`) showed the authenticated header never appearing on
**either** desktop or mobile, i.e. this app's session does not restore from cookies
plus `localStorage` at all. The likelier explanation is therefore that the mobile
browser context was simply not authenticated at that moment and was logged into
manually afterwards — not a hydration bug.

Recording it as unverified rather than guessing.

**To confirm or kill it:** log in manually on a mobile viewport (DevTools device
mode, Pixel 5), then hard-reload the landing page and sample the header from first
paint:

```js
setInterval(() => console.log(
  Date.now() % 100000,
  'loggedOutCTAs:', document.querySelectorAll('[data-testid="log-in-button"]').length,
  'userWidget:',    document.querySelectorAll('[data-testid="user-widget-button"]').length
), 250);
```

If `loggedOutCTAs: 1` appears for any measurable window before `userWidget: 1`, it is
a real flash of unauthenticated state and becomes a defect. If the user widget is
present from the first sample, this observation is closed as operator error.

### Related testability note (not a user-facing bug)
Chat message bubbles carry no `data-testid`, while every other control on the
page does. The suite therefore has to identify messages by Tailwind class
(`div.rounded-lg[class*="fit-content"]`), which is the single most
change-sensitive locator in the project. A `data-testid="agent-message"` on the
bubble and `data-testid="chat-transcript"` on the scroll container would remove
it.
